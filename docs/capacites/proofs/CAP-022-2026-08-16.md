## Contrat validé

CAP-022 fait circuler un objet métier réel avec un contexte explicite, sans le dupliquer et sans créer de publication sociale autonome.

Le lot applique la doctrine ZUMRA : le partage reste orienté vers l’action et ne crée ni like, repost, follower, score d’engagement, classement de popularité ni droit d’accès implicite.

## Implémentation prouvée

- table unique `dg_context_shares` ;
- sources actuellement raccordées : Besoin et Projet ;
- destinations : personne découvrable ou ZUMRA active dont l’émetteur est membre actif ;
- contexte de partage explicite et borné ;
- non-duplication d’un même partage source + émetteur + destination ;
- la trace historique est conservée même si la source n’est plus visible ;
- les droits de lecture de la source sont recalculés au moment de consulter le partage ;
- retirer la visibilité d’une source retire immédiatement sa présence de la boîte de réception sans supprimer la trace ;
- une ZUMRA suspendue n’expose pas son espace de partages ;
- une identité émettrice non découvrable est rendue sous le libellé neutre `Membre DG Afrique` ;
- le partage n’ajoute ni participation projet, ni adhésion ZUMRA, ni propriété, ni droit métier.

Formation et Opportunité ne sont pas simulées : elles seront raccordées lorsqu’un objet métier canonique correspondant existera dans la stack.

## Incident de preuve et résolution

Le premier scénario HTTP mélangeait successivement l’émetteur et le destinataire dans une même méthode de test avec plusieurs stubs `Http::fake()`. La création du partage était déjà prouvée en base, mais la seconde identité simulée pouvait rester contaminée par les stubs de la première.

Le scénario a été séparé en deux tests indépendants :

1. émission via les routes + preuve de l’écriture en base ;
2. réception via `/partages` avec une session Core destinataire indépendante.

Le correctif de preuve n’a modifié que `tests/Feature/ContextShareTest.php`.
